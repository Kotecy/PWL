# Аудит PWL v0.9.0 (Kotecy/PWL) — где именно тормозит

Дата: 2026-11-12. Изучен `main` @ 723b584: `main.py` (468 строк), `web/app.js` (761), `web/styles.css` (443), `web/index.html` (253).

## 0. Замеры (реальные, не оценка)

Стенд: Linux, Python 3.11, `Api` из `main.py` импортирован с заглушкой `webview`, `APPDATA` → временная папка.
Счётчики повешены на `Path.read_text` / `Path.write_text`.

| Операция | ms/вызов | чтений/вызов | записей/вызов |
|---|---|---|---|
| `get_state()` | 0.019 | 1 | 0 |
| `get_data()` (1 сервер) | 0.038 | **2** | 0 |
| `add_account()` (мелкий файл) | 0.857 | **3** | 1 |
| `update_account()` | 1.438 | **3** | 1 |
| `get_data()` (20 серверов, 111 KB) | 0.491 | 2 | 0 |
| `add_account()` (111 KB) | **6.161** | 3 | 1 |
| `set_theme()` | 0.308 | 1 | 1 |

На Windows поверх этого — NTFS + realpath-скан Defender на каждую запись. Там запись файла это
единицы–десятки ms, т.е. один клик «Добавить аккаунт» на большой базе легко стоит 20–60 ms
только на диске, при том что полезной работы там — `list.append`.

## 1. Слой данных — корень проблемы

* **Кэша нет.** `_read()` / `_read_accounts()` лезут на диск при каждом вызове моста.
* **Двойной I/O на пустом месте.** `_accounts_path()` внутри себя читает `config.json`, а иногда
  ещё и пишет его. Его зовут и `_read_accounts()`, и `_write_accounts()`. Итого `add_account` =
  3 чтения + 1 запись вместо 0 + 1 отложенная.
* **Запись целиком и синхронно.** Любое изменение (даже галка в настройках) перезаписывает весь
  JSON с `indent=2`. Файл растёт линейно → каждая операция дорожает (см. 0.86 → 6.16 ms).
* **Запись не атомарная.** `write_text` прямо в целевой файл. Выключение света / kill процесса
  в момент записи = битый JSON = `_read_accounts` молча вернёт `{}` → **все аккаунты потеряны**.
* **Глобальный `Lock` держится во время диска.** Все вызовы моста выстраиваются в очередь за fsync.
* **`except Exception: return {}`** — битый файл и отсутствующий файл неразличимы, ошибки не видны.

## 2. Запуск игры — самый дорогой путь в приложении

`launch()` → поток → `_launch_via_bat()`:
1. создать temp-файл `.bat` (`mkstemp`), записать в **cp1251**;
2. породить `cmd.exe /c bat`;
3. внутри — `chcp 1251`, `cd /d`, и только потом `start "" elementclient.exe ...`.

Три процесса, запись на диск, смена кодовой страницы — ради одного `CreateProcess`.
Плюс temp-файлы `pwl_launch_*.bat` **никогда не удаляются** (в них, кстати, лежит пароль открытым текстом).
Плюс `except Exception: pass` — если запуск не удался, пользователь просто ничего не увидит.

Надо: `Popen([exe, "startbypatcher", "nocheck", "user:...", "pwd:...", "role:..."], cwd=exe_dir)` —
один syscall, ноль файлов, ноль cmd, ошибка возвращается в UI.

## 3. Старт приложения

* Окно создаётся `hidden=True` и показывается только после `pywebviewready` →
  `await get_state()` → `await get_data()` (**два последовательных раунд-трипа**) → рендер → `show_window()`.
  До этого пользователь смотрит в пустоту.
* `pystray` + `Pillow` импортируются на уровне модуля, даже если трей выключен (Pillow — сотни ms).
* Класс-иконки: 36 файлов (`webp` + `jpg` на каждую из 18 профессий), грузятся по одному на строку.
* `setTimeout(..., 200)` для blur — костыль, добавляющий ощущение «залипания».

## 4. UI

* `renderAccounts()` пересобирает **весь `tbody` через `innerHTML` на каждый клик по строке**
  (выделение строки = полная перерисовка + повторное создание `<img>`).
* На каждую строку вешается 4 слушателя (`click`, `dblclick`, `contextmenu`, `pointerdown`) — вместо делегирования.
* `currentRowIndex()` — `indexOf` по детям на каждое событие.
* Drag-n-drop: на **каждый `pointermove`** — `getBoundingClientRect()` по всем строкам + два
  `void tbody.offsetHeight` (принудительный синхронный reflow). Это и есть источник рывков.
* `shuffleGlyphs()` вызывается при каждом рендере → **эмблемы серверов случайно меняются** при
  любой перерисовке. Это баг, а не фича.
* `innerHTML` с неэкранированными `nick` / `login` / `comment`: ник с `<` или `&` ломает вёрстку,
  а `<img src=x onerror=...>` в комментарии — это исполнение кода в контексте приложения.
* Пагинация по 4 сервера вместо нормального скролла; смена страницы = полный рендер.

## 5. Архитектура и корректность

* **Два источника правды**: массив `servers` в JS и JSON на диске, мутируются независимо
  (`servers.push(...)`, `currentServer.accounts.splice(...)`) и синхронизируются вручную.
* **Идентичность аккаунта = индекс в массиве.** Перетаскивание строк меняет индексы →
  редактирование/удаление после drag может попасть не в тот аккаунт.
* `delete_server(keep_accounts=True)` складывает аккаунты в `kept_accounts`, откуда их
  **никто никогда не достаёт**. «Сохранить аккаунты» = потерять аккаунты.
* Пароли — plaintext JSON. Имя файла из 7–15 случайных цифр —.security theater, а не защита.
* `Api` держит `_window` приватным из-за того, что pywebview интроспектит публичные атрибуты —
  симптом того, что бридж и домен слиплись в один класс.
* Мёртвый код: `launch_mode` всегда `bat`, второй режим отключён, но UI/метод/настройка остались.

## 6. Что делать (целевая архитектура)

```
core/      домен: Server, Account (стабильный uuid), инварианты — без I/O, тестируется
store/     один снапшот в памяти + атомарная отложенная запись (tmp+replace),
           дебаунс 150 ms, миграция со старого формата, журнал на случай краша
services/  launcher (один CreateProcess), secrets (DPAPI), tray (ленивый импорт), window
bridge/    тонкий RPC: bootstrap() отдаёт всё состояние одним вызовом,
           мутации возвращают патч, события пушатся в UI
ui/        единый store + точечный рендер по ключам, делегирование событий,
           виртуальный скролл, drag на transform без reflow, экранирование всего
```

Ожидаемо: 0 чтений диска на вызов моста вместо 2–3, одна отложенная запись вместо N синхронных,
один процесс вместо трёх на «Войти», первый кадр до загрузки данных.
